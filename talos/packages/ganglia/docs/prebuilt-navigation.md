# 预构建导航资产与按需加载

2026-11-07。以下区分现有实现、隔离实验和下一阶段方案。逐点冷启动数据见
[38 点对照](per-point-performance.md)。冻结输入来自升级 v74 前的成功请求。

## 当前的表面与计算过程

`buildGroundSurfaces` 从关卡选定的真实碰撞三角形建立可站立支撑面。输入包括地板、
楼梯、障碍和顶棚，使用角色半径、高度、坡度、上台阶及下台阶参数。
`buildSupportField` 调用已编译为 WASM 的 Recast 执行体素化、净空筛选、相邻高度连接、
半径侵蚀、区域及轮廓生成，最后生成导航多边形和细节高度三角形。

当前导出逐个输出细节三角形，每个三角形成为一个 `Surface`。后续图以这些面为节点。
原始导航多边形与细节三角形的所属关系在导出时丢失。因此细节精度也直接推高图的规模。
在真实碰撞输入的一个 38.4 米瓦片诊断中，0.15 米分辨率产生 4,464 个导航多边形与
14,422 个细节三角形。0.05 米分辨率为 21,229 个多边形与 40,439 个细节三角形。
这个诊断采用选区内原始碰撞，尚未重放导出器的全部可行走层筛选，数值用于分析表示规模。

默认瓦片边长为 `256 × 0.15 = 38.4` 米。带 padding 的原生网格已按内容指纹保存在磁盘，
请求仍需裁剪 core、拼接接缝，再生成 JS 邻接图、投影索引、支撑追踪索引、连通分量及动作检索。
`createGroundPlanner` 包含这些准备。目标附近以三倍水平精度进行局部修补时，会再次对合并后的
全部表面调用它。38 个固定请求中有 31 个追加了修补面，追加面数中位数仅 134。

落脚点通常从现有支撑面投影和采样。跳跃/下落还需计算起落位置、水平控制、滞空时间、
完整胶囊碰撞及资源条件。这些查询相关动作与静态支撑网格具有不同生命周期。

## 预构建范围

全场景可离线构建的资产包括支撑网格、权威定向通道、接缝所有权、连通分量、空间索引、
碰撞块及索引、固定设备动作和区域入口/出口关系。当前默认采用任务完成、设施启用和供电、
门打开的统一配置，适合建立一种明确绑定的静态版本。

查询提供起点、目标交互体和资源状态，搜索由此产生标签。连续起落位置及速度无法全部枚举。
共享动作资产应保留有验证范围的候选族，再在查询中验证目标接入和必要的局部细化。
完整精细网格也不能自动消除大量动作候选和全域搜索。

建议保留 Recast 导航多边形、其细节高度引用和权威通道，以多边形或有语义约束的区域承载连通，
以细节三角形承载高度及接触查询。不同楼层、单向落差、楼梯、窄口和资源转移必须显式保留。
区域入口/出口的压缩关系需要与未压缩参考解比较。此方案对应 G3，共享区域资产尚未实现。

## 动态加载与边界

建议分三层组织资产。

1. 场景 manifest 和粗区域图提供稳定 ID、区域范围、版本、资产大小及块依赖。
2. 搜索经过的区域加载导航块，包含多边形、定向通道、入口/出口转移、局部索引与设备边。
3. 精细接触和动作验证加载相关支撑细节、碰撞块及必要的邻区 halo。

高楼的多个高度层应归属于同一 XZ 分块的显式分层数据。长距离搜索先确定区域走廊，沿途按需加载，
并保留粗图的区域连通关系。缺失数据应触发加载或扩展搜索。块接缝需要稳定的所属区域、方向和依赖，
在卸载邻块时仍能识别待加载出口。

局部裁剪后重新推断边归属存在回归风险。一个长边在窗口外发生多重覆盖，当前保守规则会禁用整条边。
只加载窗口内两个面再重算归属，可能重新开放原本阻挡的通道。因此接缝和歧义边状态应由离线全量
来源计算并保存。局部细化需要明确替换、拼接及失效规则。

资产键需要绑定游戏构建、几何生成器、角色尺寸、体素和台阶参数、选择配置、物理层及状态策略。
变更应失效受影响的块与边界依赖。512 瓦片是当前单次 CLI 预算，全场景离线构建需要批次和 manifest。

## 体积实测与估算

对 `0bzZEM3` 冻结局部输入进行无量化 f64/u32 打包。它有 297,729 个面、259,159 个共享顶点、
750,800 条图边和 131,071 个 BVH 节点。gzip 使用 level 6，各段独立压缩。

| 内容 | 原始体积 MiB | gzip MiB |
| --- | ---: | ---: |
| 现有地面 JSON | 61.90 | 5.80 |
| 共享顶点、面索引和偏移 | 10.51 | 3.59 |
| 上述几何加图、普通通道和 BVH 的实验负载 | 60.10 | 16.70 |
| 选定碰撞 JSON | 301.80 | 未测 |
| 碰撞顶点 f64 和索引 u32 | 146.92 | 81.31 |

实验负载包括图成本、面中心、普通通道的 owner/区间及完整 BVH。尚未包含导入接缝完整数据、
标识符和 manifest、控制器/楼梯元数据、碰撞 BVH、动作证明及资源标签。它是负载测量，
完整可加载格式和生产加载器仍待实现。预先保存索引会增加传输内容，同时减少运行时准备。
碰撞资产需要独立分块和去重，完整查询矩形中的碰撞应拆分为局部验证依赖。

现有缓存中 389 个不同内容指纹记录合计 797.5 MiB，单文件中位数为 1.97 MiB。
这些记录包括不同版本/参数，不能直接作为全场景瓦片数量。中位样本有 10,527 个三角形，
其精确共享顶点与索引负载为 0.294 MiB，尚未计索引和邻接。

v74 viewer manifest 的有内容单元覆盖映射到当前 ground grid，map01 约 1,637 个瓦片，
map02 约 4,104 个瓦片。加入一圈 halo 为约 1,899 与 4,732 个。按现有缓存 JSON 中位大小
外推，前者合计约 11 GiB，仅含当前表示的支撑面。完整 root 矩形外推约 28 GiB。
密度、空块、楼层和高精度配置会改变结果。完整离线包的最终大小必须通过整图构建清单测量。
这些覆盖与缓存外推尚未形成实际全图构建。

## WASM 试验与下一阶段验收

隔离的 C/WASM 原型实现相同的 f64 BVH 分区与最近邻堆顺序。真实局部输入的三轮组件测量中，
JS 构建中位数 151.8 ms，WASM 内核为 86.1 ms。计入初始化、打包和 JS 对象重建后为
138.2 ms。保留 WASM 内部树时，120 次最近邻查询中位数为 5.84 / 2.04 ms。
完整树和查询前缀一致。三轮共享同一个 Node 进程，畸形输入、分量过滤和完整路线仍待验证。

适合的后端边界是连续数组中的几何、索引、投影、邻接和图遍历，并通过批量接口运行。
WASM 代码原型只有 4,120 字节，场景数据与运行状态决定内存规模。
[WebAssembly Memory 文档](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Memory)
描述了可由 JS typed array 访问的线性内存。Recast 的 tiled mesh 接口也提供分块加载和卸载机制。
[Recast tiled mesh 参考](https://recastnav.com/group__detour.html)

下一阶段先构建一个覆盖楼梯、多层、下降和设备的区域，保存多边形/细节关系、权威通道和二进制索引，
验证全加载和按需加载结果。测量首条路线、最终结果、读入字节及峰值内存，再扩大到两张地图。
旧成功请求需要保持可达且实际路线成本不增加，原有参考路线应保留用于对照。
当前 38 点通过 alpha.53 的完整对象对照，另有 10 点的历史质量差异仍在待修列表。
